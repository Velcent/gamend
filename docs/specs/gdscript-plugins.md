# GDScript plugins — GDScript transpiled to Elixir source

Design spec for a new roadmap item. Goal: let a Godot developer write server
hooks in **GDScript**, transpiled to readable **Elixir source**, compiled by
`mix` into an ordinary OTP plugin. No Elixir knowledge required, no new runtime,
no sandbox, and native BEAM speed — the compiled output is indistinguishable
from a hand-written plugin.

## Status

**Steps 2 and 3 of the DoD are built and verified.**
`sdk_tools/lib/gamend/gdscript/` holds the lexer, parser and codegen;
`mix gamend.gdscript.compile` is wired with a `--check` staleness gate;
`modules/plugins_examples/example_gdscript` is a working plugin that loads into
a running server, grants currency, sends a notification and walks a list with
`break` / `continue`.

Built: `func` with default args, `var` / `const`, assignment and compound
operators, `if` / `elif` / `else` and `for` / `while` **including the mutation
lift through both**, `break`, `continue`, `return` (tail and early),
arithmetic, comparison, `and` / `or` / `not`, arrays, dictionaries, indexing,
field access, context calls, local calls, `range()`, and `opts({...})` for
keyword-list arguments.

Also built: `match` (literal, multi-pattern, `var` bind and `_`), lambdas with
`.call()`, `spawn()` / `await` for concurrency, `Vector2` / `Vector3` / `Color`
as value types, single-line bodies (`if ready: return true`), and
**reference semantics for Arrays and Dictionaries** with element assignment.

Also built: **Array, Dictionary and String methods** -- 30 names over 27
helpers, each dispatching on the receiver at run time, with the mutating ones
going through the heap.

Also built: the **`@GlobalScope` builtins** (~80 of them: trigonometry,
interpolation, `clamp` / `lerp` / `snapped` / `wrap*`, the random family, the
`print` family), **`JSON`** and **`Time`** as static classes, and the
**`Vector2` / `Vector3` methods** (`length`, `distance_to`, `normalized`,
`dot`, `cross`, `rotated`, ...). See "The class surface" below for what was
deliberately left out.

Also built: **signals** (`signal` / `.emit()` / `await`, on the new
`Gamend.Signals` context), top-level `const` and `enum`, `static func`,
ternary, `is` / `as`, `assert()`, `%` string formatting, typed-array
annotations, array and dictionary patterns in `match`, `d.get` / `d.set`, and
the numeric and conversion builtins (`abs`, `floor`, `ceil`, `round`, `min`,
`max`, `int`, `float`, `typeof`).

Also built: **inner classes** with `extends`, `_init`, field access through an
implicit `self` and one generated dispatcher, **`Context.callv(name, args)`**
for calling by computed name inside the whitelist, **cross-script calls** via
`class_name`, and the **Array / Dictionary / String method sets taken from the
Godot class reference** rather than from memory.

Not built, and decided rather than pending: **static type enforcement**. It
would buy correctness only -- there is no Variant dispatch on the BEAM to
bypass, so unlike Godot it buys no speed -- and `gdlint` already checks for
missing annotations outside the compiler. Type hints keep parsing and are
discarded.

Not possible: any engine type.
Everything unsupported is a compile error naming the line.

`sdk_tools`' tests and the `gen/` staleness gate run in CI (`test-sqlite` and
`lint` in `build-and-check.yml`).

The API table is now **generated by `mix gen.sdk`** into
`sdk_tools/lib/gamend/gdscript/api.ex` -- 25 contexts with every public arity,
so adding an SDK context makes it callable from a script with no change to the
compiler, and a wrong argument count or a misspelled function is a compile
error with a suggestion. `mix gamend.gdscript.new` scaffolds a plugin, and
[the guide](../../priv/docs/40-gameplay/95-gdscript-hooks.md) is written.

Two contexts (`Gamend.Cache`, `Gamend.Hooks`) have hand-written stubs and sit
outside `@sdk_modules`, so `gen.sdk` folds them in from an explicit
`@extra_api_modules` list -- without that a script silently loses
`Hooks.caller_user/0`, which is how an RPC learns who called it.

## Why (the hook API is fine; Elixir is the toll booth)

`Gamend.Hooks` already exposes **80 callbacks** and the SDK exposes **26
contexts** (`Gamend.Economy`, `Gamend.Lobbies`, `Gamend.Quests`, …). The
extension surface is not the problem. The problem is the cost of the first line:
a Godot developer who wants to grant 100 gold on registration must learn Elixir,
the OTP application layout, `mix.exs`, and `mix plugin.bundle`.

Nakama shipped Lua and JavaScript runtimes for exactly this reason. Gamend's
audience is narrower and therefore easier to serve: they already write GDScript.

**This is a front end on the plugin system, not a new one.** Nothing about
hooks, plugin loading, `hooks_module`, or bundling changes. The output is
`.beam` files in `<plugin>/ebin` — byte-for-byte the shape `mix plugin.bundle`
produces today.

## What this is not

- **Not a sandbox.** A GDScript plugin is as trusted as an Elixir plugin — it is
  code the server operator installed. Untrusted third-party scripts are a
  different product (see Deferred).
- **Not Godot.** No nodes, scenes, physics, `Resource`, `preload`, `_process`.
  There is no engine and no frame loop on the server.
- **Not all of GDScript.** A documented subset, rejected at parse time rather
  than failing at runtime.

## Shape

```
shop.gd  →  lexer  →  AST  →  codegen  →  gen/shop.ex  →  mix compile  →  ebin/*.beam
```

The generated `.ex` is **written to disk and kept**. It is `mix format`ted,
readable, diffable, and it is what appears in stack traces. That file is the
debugging story for v1 — a user who hits an error reads generated Elixir that
looks like their GDScript.

## Plugin layout

```
modules/plugins/my_game/
  scripts/
    hooks.gd                     ← author writes this
  gen/
    gamend/modules/my_game.ex    ← generated, committed
  mix.exs                        ← generated once by `mix gamend.gdscript.new`
  ebin/                          ← mix plugin.bundle output, unchanged
```

Two tasks in `sdk_tools/lib/mix/tasks/`, next to `plugin.bundle`:

- `mix gamend.gdscript.new <name>` — scaffolds the directory, `mix.exs` with
  `hooks_module:` already wired, and a `hooks.gd` with one example callback.
- `mix gamend.gdscript.compile` — `scripts/*.gd` → `gen/**/*.ex`. Runs before
  `compile` via a compiler alias so `mix plugin.bundle` is unchanged.

The admin "Build bundle" control gains a GDScript step. Nothing else in the
admin or loader moves.

## The mapping that makes this cheap

GDScript's static-call syntax is Elixir's module-call syntax. That is the whole
trick, and it means the 26 SDK contexts need **zero** translation work — they
are already shaped like GDScript singletons.

```gdscript
func after_user_register(user):
    Economy.grant(user.id, "gold", 100, "welcome_bonus")
    Notifications.create(user.id, "welcome", {"gold": 100})
```

```elixir
def after_user_register(user) do
  Gamend.Economy.grant(user.id, "gold", 100, "welcome_bonus")
  Gamend.Notifications.create(user.id, "welcome", %{"gold" => 100})
  :ok
end
```

| GDScript | Elixir | Note |
|---|---|---|
| `Economy.grant(...)` | `Gamend.Economy.grant(...)` | prefix the known context list |
| `user.id` | `user.id` | hook payloads are structs; dot access works as-is |
| `{"a": 1}` | `%{"a" => 1}` | Dictionary → string-keyed map |
| `d["k"]` and `d.k` | `d["k"]` | always emit bracket form; `.k` on a map raises |
| `[1, 2, 3]` | `[1, 2, 3]` | Array → list |
| `func f(a, b = 2)` | `def f(a, b \\ 2)` | default args map directly |
| `null` / `true` | `nil` / `true` | |
| `"%s scored %d" % [n, s]` | `GDScript.Runtime.format(...)` | runtime helper |

Unknown identifiers are a **compile error at name resolution**, not a runtime
`UndefinedFunctionError`. The API table is generated from `@sdk_modules`, so it
never drifts from the SDK.

## Mutation — the only genuinely hard part

Elixir allows rebinding (`x = 1; x = x + 1`). What it does not allow is a
rebinding inside a block escaping that block. Codegen needs one analysis pass:
**for each block, the set of variables assigned inside it**, threaded through as
a tuple. Three cases.

**`if` — the assignment becomes the return value**

```gdscript
var bonus = 0
if score > 100:
    bonus = 50
```
```elixir
bonus = 0
bonus = if score > 100, do: 50, else: bonus
```

**`for` — `Enum.reduce` over the assigned set**

```gdscript
var total = 0
var count = 0
for r in rounds:
    total += r
    count += 1
```
```elixir
{total, count} =
  Enum.reduce(rounds, {total, count}, fn r, {total, count} ->
    {total + r, count + 1}
  end)
```

**`while` — one runtime helper plus recursion**

```elixir
# GDScript.Runtime
def while_loop(acc, cond_fn, body_fn) do
  if cond_fn.(acc), do: while_loop(body_fn.(acc), cond_fn, body_fn), else: acc
end
```

Generated binder names are suffixed (`total__1`) rather than reusing the source
name, so nothing depends on Elixir's shadowing rules and the output is
unambiguous to read.

**Mutating methods count as assignment.** `arr.append(x)` and `d[k] = v` mutate
in GDScript and must be lifted to rebinds, then joined into the same assigned
set:

| GDScript | Elixir |
|---|---|
| `arr.append(x)` | `arr = arr ++ [x]` |
| `arr.erase(x)` | `arr = List.delete(arr, x)` |
| `d[k] = v` | `d = Map.put(d, k, v)` |
| `d.erase(k)` | `d = Map.delete(d, k)` |

The mutating-method list is closed and lives in one table; a collection method
outside it is a compile error rather than a silent no-op. That last part
matters — `arr.append(x)` compiling to a discarded value would be the worst
possible failure mode.

## Return, break, continue, await

| Problem | Emission |
|---|---|
| `return` in tail position | plain value, no wrapper |
| `return` anywhere else | body wrapped in `try do … catch {:gd_return, v} -> v end`, emit `throw({:gd_return, v})` |
| `break` / `continue` | `Enum.reduce_while` with `{:halt, acc}` / `{:cont, acc}` |
| `await` | `receive do {:gd_signal, ^ref, v} -> v after t -> nil end` |

`await` deserves a note: the script runs in its own BEAM process, so a
suspended coroutine is a blocked process — a few KB and zero CPU. Ten thousand
scripts can await concurrently, which the engine itself cannot do as cheaply.
The `try/catch` wrapper is emitted **only** when a non-tail `return` exists, so
the common hook pays nothing for it.

## The v1 subset

| Supported | Rejected at parse (with a "not supported server-side" message) |
|---|---|
| `var`, `const`, all assignment operators | `_ready`, `_process` — there is no frame loop |
| `if` / `elif` / `else` | `signal` declarations (use `Gamend.Realtime`) |
| `for`, `while`, `break`, `continue`, `range()` | `preload`, `load`, `@onready`, `@tool` |
| `func`, default args, `return` | `_ready`, `_process`, `_physics_process` |
| `Array`, `Dictionary`, `String`, `int`, `float`, `bool` | `Node`, `Resource`, `Object`, any engine type |
| `opts({...})` for keyword arguments | implicit keyword inference from position |
| type hints — **parsed and discarded** | static type *enforcement* |
| `match` (literals, `var`, `_`, alternatives) | ternary, `match` array/dict patterns |
| lambdas, `.call()`, `spawn()`, `await` | `yield` (4.x removed it anyway) |
| `Vector2`, `Vector3`, `Color` as value types | `set`/`get` property accessors |
| single-line bodies | operator overloading beyond the value types |

Type hints parse but do not check. They are kept in the AST so a later pass can
turn them into guards without a grammar change.

## Errors and debugging

v1: stack traces point at `gen/my_game.ex`, and every generated file carries a
header naming its source `.gd` plus a `# gd: hooks.gd:42` comment on each
emitted statement group. A user reading the trace lands on generated Elixir
next to a comment naming their line.

v2 (deferred): parse the generated source back with `Code.string_to_quoted/2`,
rewrite `line:` metadata from a side-map, and `Code.compile_quoted(quoted,
"hooks.gd")`. Traces then name the `.gd` file and line directly. This is
strictly additive — the emitted `.ex` stays the artifact of record.

## Testing

- **Golden files** — `test/fixtures/gdscript/<case>.gd` +
  `<case>.ex.expected`. The suite compiles and diffs. Cheap to add, and the
  diff is the review surface for every codegen change.
- **Behavioural** — each fixture is compiled, loaded, and *called*, asserting
  the returned value. Golden output that compiles to the wrong semantics is the
  failure mode golden tests alone miss.
- **The mutation matrix explicitly** — nested `if` inside `for` inside `while`,
  each mutating a different overlapping variable set. That is where the
  assigned-set analysis breaks, and nowhere else.
- **One real plugin** — port `modules/plugins_examples/example_hook` to
  `modules/plugins_examples/example_gdscript` and assert identical behaviour
  against the existing test.

## What building it changed

Four things the design above got wrong or did not anticipate.

- **Tail position must be threaded from the function, not recomputed per
  block.** A `return` as the last statement of an `if` branch looks like a tail
  return to a per-block check, so it emitted a bare value and execution fell
  through to the next statement. Silently wrong output, caught only by running
  the code. `gen_statements/4` now carries `tail_ok?`, false inside every
  branch.

- **Generated code must be warning-clean, and that took real work.** Two
  separate causes. Multi-clause helper functions get narrowed by Elixir's type
  checker from the call sites in the generated module, which then warns "this
  clause is never used" -- so every helper is one clause with an internal
  `cond`. And `var x = 0` followed by an `if` that assigns `x` in every branch
  is a dead store, which warns "variable is unused" -- so codegen does a small
  liveness check and emits `_ = <initializer>` instead. This matters beyond
  tidiness: routine warnings would drown out the real ones, and the whole
  argument for emitting *source* is that the Elixir toolchain becomes free
  codegen QA.

- **GDScript cannot express a keyword list**, and the fix this spec first
  proposed -- "a trailing Dictionary argument becomes a keyword list" -- is
  **wrong**. `Notifications.admin_create_notification(sender, recipient, attrs)`
  ends in a Dictionary that is a *payload map*. Inferring options from position
  would have silently corrupted it, which is exactly the class of failure the
  whole design is meant to refuse. The conversion is therefore explicit and
  local:

      Economy.grant(user.id, "gold", 100, opts({"reason": "welcome"}))
        ->  Gamend.Economy.grant(user.id, "gold", 100, reason: "welcome")

  `opts` is a reserved builtin (a `func opts` is a compile error), takes exactly
  one Dictionary literal, and its keys must be plain lowercase identifiers --
  so the atoms it emits are bounded by the script's own text and nothing can
  smuggle arbitrary Elixir through a key. Signature-driven inference could be
  layered on later without breaking this spelling.

- **The SDK stubs dropped default arguments -- fixed.** `Gamend.Economy.grant/4`
  has `opts \\ []` in core, so `grant/3` exists at runtime, but the generated
  stub declared only `grant/4`, and any plugin calling the shorter form -- in
  any language -- got a spurious "undefined or private" warning. `mix gen.sdk`
  now re-emits the defaults. Doing so exposed a latent bug in the same task:
  argument lists were parsed with `~r/[\w!?]+\(([^)]*)\)/`, which stops at the
  first `)` and so truncated `now \\ DateTime.utc_now()` to
  `DateTime.utc_now(`. Harmless while only names were read; it emitted
  unparseable Elixir as soon as defaults were. Both now use a balanced-paren
  scan that also splits on top-level commas only.

- **A wrapped statement must end on the line its brackets close.** The lexer
  suppressed the statement terminator for every continuation line, including
  the one that balanced the brackets, so a multi-line call ran straight into
  the following statement. The original "calls may wrap across lines" test
  missed it because the wrap ended a block, and the dedent terminated the
  statement anyway -- the real example plugin was what caught it. There is a
  regression test now with a statement after the wrap.

## What step 3 changed

Loops are the same fold as `if`, threading the assigned set through iterations
instead of branches, with `break` / `continue` throwing the accumulator out so
they work at any nesting depth. What that cost:

- **`while` tagged its body twice.** `gd_while` expects `{:cont, acc}` /
  `{:halt, acc}`, and the jump-handling `try/catch` already produced one -- then
  the emitter appended `{:cont, acc}` on top, discarding the `:halt`. A `break`
  inside a `while` looped forever. Caught by a test that hit the 60s timeout,
  which is the only reason it was not a hang in somebody's server.

- **Every binder needs the liveness check, not just `var`.** Three separate
  warning sources appeared: an accumulator bound in a `fn` head that the body
  overwrites before reading, a loop variable the body never uses, and the result
  binder of an `if`/loop that nothing afterwards reads. All three are the same
  question the dead-store analysis already answered, so all three now take
  `_name`.

- **...and fixing the last one introduced a real correctness bug.** A branch
  body ends in the lifted tuple, which *reads* those names even though no
  statement mentions them. Dropping a nested lift's binding on that basis made
  the tuple carry the stale outer value -- `f(1,1)` returned `[10, 2]` instead
  of `[30, 20]`. The existing nested-`if` test caught it immediately. Codegen
  now threads `tail_reads` so an enclosing block declares what its tail will
  read.

- **`reads?` was wrong for compound assignment.** It answered `op != "="` --
  true for *every* name, not just the assignment target -- so `y += 1` reported
  `x` as read. Everything built on it (dead stores, all three `_name`
  decisions) was silently disabled. Only visible once the loop-variable check
  started depending on a precise answer.

- **`gd_` is now a reserved identifier prefix.** Codegen emits helpers and
  internal binders into the same module, so a `func gd_add` or `var gd_acc`
  could shadow one and change what a script's own arithmetic means. That hole
  existed from step 2 and was closed here.

## What the API table changed

- **The hardcoded list was already wrong.** It named `Cache`, which is not in
  `@sdk_modules`, and would have gone stale the moment a context was added.
  Generating it surfaced the real split: `@sdk_modules` drives the *generated*
  stubs, but `sdk/` also holds two hand-written ones that are equally callable.

- **Arities came free and are worth more than the context list.** The table
  carries every public arity, so `Economy.grant(u, "gold")` is now
  "takes 3 or 4 argument(s), called with 2" at compile time instead of an
  `UndefinedFunctionError` in a hook at 3am. Near-miss suggestions
  (`did you mean \`grant\`?`) come from `String.jaro_distance/2` over the same
  table.

## What the last four features changed

- **`spawn()` is an invention, and that is a real cost.** Godot has no `spawn`:
  there `await` waits on a **signal** or a coroutine, and nothing emits signals
  server-side, so `await` alone would have nothing to wait for. Pairing it with
  `spawn(lambda)` (`Task.async`) makes it useful -- two independent lookups cost
  one round trip -- but it puts a name in the language that a Godot developer
  will not find in any Godot documentation, which is exactly the uncanny-valley
  risk this spec opens by warning about. It is documented as a server extension
  rather than presented as GDScript. The alternative spellings both have costs:
  `Thread`/`WorkerThreadPool` are engine classes with stateful three-call APIs,
  and dropping the feature leaves `await` meaningless.

  **There is a better answer, found after this shipped:** plugin-scoped signals
  on `Gamend.PubSub` (see "What remains" below) would give `await` the thing
  Godot gives it, at which point `spawn()` is an optional extra rather than the
  prop holding `await` up. Build signals before deciding whether `spawn` stays.

  Caveats, both documented: a spawned lambda does not inherit the hook's caller
  (`Hooks.caller_user/0` returns nothing inside one), and `await` gives up after
  30 seconds.

- **A multi-line lambda cannot live inside brackets**, because the lexer emits
  no line structure between `(` and `)` -- everything there is one logical
  line. Godot's own lexer special-cases this; ours does not. It is refused with
  advice ("assign it to a variable first") rather than the confusing
  "expected an expression, got `var`" it produced first.

- **`match` needed a fallback clause.** A GDScript `match` that matches nothing
  does nothing; Elixir's `case` raises `CaseClauseError`. Codegen appends
  `_ -> <tail value>` whenever the script has no `_` or `var` case, so the
  semantics carry over instead of turning a silent no-op into a crash.

- **Value types made `-` and `*` join the helper set.** `+`, `/` and `%`
  already went through helpers because GDScript disagrees with Elixir on them;
  supporting component-wise vector arithmetic meant `-` and `*` had to as well.
  That is the cost side of the trade already recorded above -- every arithmetic
  operator is now one function call -- and the same reasoning applies: on a
  path dominated by database writes it does not register, and a type-inference
  pass can specialise the provably-numeric cases later. A value type is
  identified at run time by having only component keys (`:x`, `:y`, ...), which
  is what keeps an ordinary Dictionary (string keys) out of the vector branch.

- **`gd_get` was over-reported for member calls.** `a.b()` is a call, not a
  field read, but the helper scan treated the `:member` node the same either
  way -- so a script using only method calls emitted an unused `gd_get` and
  warned. Latent since step 2; it only surfaced once lambdas made
  method-call-only scripts possible.

## What remains, and what cannot be supported

Nothing in the first table is hard. Most of it is a table entry and a helper;
the reason it is not built is sequencing, not difficulty.

### Can be built

| Feature | Maps to | Size |
|---|---|---|
| ~~Non-mutating methods~~ — `size`, `has`, `keys`, `values`, `find`, `split`, `to_upper`, … | **shipped** — one helper per method, each dispatching on the receiver's type at run time | — |
| ~~Mutating methods~~ — `append`, `erase`, `clear`, `insert`, `sort`, `merge`, … | **shipped** — `gd_store` on the per-hook heap | — |
| ~~Element assignment~~ — `d[k] = v`, `d[k] += 1`, `xs[i] = v` | **shipped** | — |
| ~~Reference semantics for Array / Dictionary~~ | **shipped** — see the section below | — |
| ~~Ternary~~, ~~`is`~~ / ~~`as`~~, ~~`assert()`~~, ~~`%` formatting~~, ~~typed arrays~~ | **shipped** | — |
| ~~`enum`, `static func`, top-level `const`~~ | **shipped** — constants and enum members fold into the code that uses them | — |
| ~~`signal` + `.emit()` + `await sig`~~ | **shipped** — `Gamend.Signals`, a real context, on `Phoenix.PubSub` | — |
| ~~Array and dictionary patterns in `match`~~ | **shipped** — Elixir patterns, with a size guard so a closed dictionary pattern means what Godot means | — |
| ~~A context call by computed name~~ | **shipped** as `callv` -- the allowed `{name, arity}` list is emitted into the module and `apply/3` is guarded by it, so nothing outside the table is reachable | — |
| ~~`class_name`, inner classes, inheritance~~ | **shipped** -- instances are tagged Dictionaries, methods are private functions, and dispatch is one generated `case` over `{class, method, arity}` resolved through `extends` at compile time | — |

**Signals deserve their own note, because they change the `spawn()` story.**
Plugin-scoped signals need no cross-script references at all: a `signal foo`
declared anywhere in a plugin claims the topic `gdsignal:<plugin>:foo`, so any
script in that plugin can `foo.emit(...)` and any other can `await foo`.
`Gamend.PubSub` already carries it, already works across a cluster, and
`realtime_events/0` is the existing precedent for declaring an event name.

That would make `await` mean what it means in Godot, and it is the strongest
argument for revisiting `spawn()` — with real signals, `await` is no longer a
keyword propped up by an invented builtin. The one wrinkle is the same race
Godot has: `await` subscribes at the await point, so an emit before that is
missed. Subscribing at function entry for every signal the function awaits
would close it.

`connect(callable)` is the murkier half — a listener needs a lifetime, and a
hook already *is* the server's listener model. `emit` + `await` is the pair
worth building; `connect` should wait for a concrete use.

**A note on the whitelist, since "dynamic dispatch" was wrongly listed as
impossible.** The whitelist is not a security wall today -- scripts are as
trusted as an Elixir plugin. It buys two things: a typo is a build error rather
than a 3am `UndefinedFunctionError`, and *if* gamend ever hosts other people's
scripts, codegen has no path that emits a call outside the table. Resolving a
name at run time gives up the first for the calls that use it, and keeps the
second as long as the lookup is **in the table**. That is a legitimate trade,
not a barrier. Only unbounded `apply/3` breaks it.

One hard constraint on any such feature: look names up **as strings**. Calling
`String.to_atom/1` on script-supplied data grows the atom table without bound
and eventually takes the node down.

### Reference semantics -- SHIPPED, via the per-hook process heap

An earlier revision of this spec listed reference semantics under "cannot be
built", by analogy to Luerl. That was wrong, and the analogy was wrong too:
Luerl is slow because it *interprets* and threads its whole VM state through
every call; its table store is the same structure proposed here and is not the
slow part.

**The heap already exists.** Every hook and RPC runs in its own `Task.async`
process (`safe_apply_with_caller`), and gamend already keeps per-hook state in
that process's dictionary (`:gamend_hook_caller`). The process dictionary is a
mutable heap that is scoped to one hook, needs no cleanup -- it dies with the
Task -- and costs a hash lookup to read.

**Design.**

- `[]` / `{}` literals allocate: `gd_new(value)` stores the value under a
  `make_ref()` and returns `{:gd_ref, ref}`. `var b = a` copies the ref, which
  is aliasing for free.
- Every helper that touches a collection (`gd_index`, `gd_add`, `gd_truthy`,
  `gd_eq`, iteration) calls `gd_load/1` first: one pattern match on
  `{:gd_ref, _}`, falling through for anything else. The helpers are already
  the only places collections are touched, so codegen barely changes.
- A mutation is `gd_store(ref, fn)`. `d["a"]["b"].append(x)` resolves the path
  through refs and stores at the leaf -- nested aliasing works without
  `update_in`.
- Each `func` compiles to a public wrapper and a private body:
  `def f(a), do: gd_deref(gd_f(gd_box(a)))` and `defp gd_f(a)`. Local calls go
  to `gd_f`, so refs pass straight through; gamend calls the wrapper. The
  split is compile-time, zero run-time check. `gd_box/1` deep-walks lists and
  maps into refs, leaving structs and value types (`Vector2`) alone;
  `gd_deref/1` is its inverse. Context-call arguments are `gd_deref`'d.
- `==` on collections deep-derefs both sides, because Godot compares contents.
- **Optimization that makes ordinary hooks free:** only box a function's
  parameters when the body mutates through one of them, which is detectable at
  compile time. Nearly every hook only reads its payload, so pays nothing at
  the boundary.

**Measured** (`sdk_tools/bench/heap_bench.exs`, M1, 1M iterations):

| operation | value | heap | delta |
|---|---:|---:|---:|
| `Enum.at(xs, 50)` | 97 ns | 143 ns | +46 ns |
| `Map.get(d, k)` | 39 ns | 55 ns | +16 ns |
| `length(xs)` | 108 ns | 153 ns | +45 ns |
| build a 1000-element array in a loop | 931 µs | 955 µs | +2.6% (both O(n²) from `++`, as today) |
| box + deref a `user` payload | -- | 5 µs | boundary, and skipped when the body does not mutate |
| box + deref a 20-item purchase | -- | 66 µs | likewise |
| box + deref 10,000 records, once | -- | 35 ms | the one bad case: huge RPC arguments, already O(n) to decode |

And the semantics come out exactly as Godot: `var b = a; b.append(3)` shows in
`a`; `add_reward(rewards)` mutates the caller's array; `d["items"].append(1)`
shows in `d`.

**Residual differences, all honest and all cost tiers rather than walls:**

1. A `spawn()`ed lambda runs in another process with its own dictionary, so it
   sees a **snapshot**. Godot's threads share the heap under a mutex. Closable
   with ETS if anyone needs it; nobody has.
2. Temporaries live until the hook returns -- there is no refcounting. A loop
   that creates a million throwaway arrays holds all of them. Hooks are short;
   document it.
3. The generated `.ex` gains `gd_new` / `gd_load` / `gd_store` / `gd_box` /
   `gd_deref`, so "reads like your GDScript" weakens a little. Most of it lives
   inside helpers that already exist.

**Effort:** medium -- comparable to the loops work. Every collection touch
already goes through a helper, which is where `gd_load` goes; the
wrapper/body split is mechanical.

**Shipped.** `d[k] = v`, `d[k] += 1` and `xs[i] = v` work through any path, a
callee mutates its caller's collection, two names alias one collection, and `+`
makes a new one -- all matching Godot, all covered by tests. The example plugin
exercises it (`tally_items` / `bump`).

Three things the build turned up:

- **The module-level switch works exactly as hoped.** A script with no
  in-place mutation emits no `gd_new`, `gd_load`, `gd_box` or `gd_fn_` at all,
  so every script written before this is byte-identical and pays nothing.
- **Wrapping needs a peephole to stay readable.** Wrapping every operand in
  `gd_load` produced lines like
  `gd_truthy(gd_load(gd_deref(item) == gd_deref("")))`. Literals, comparisons,
  logical operators, non-`+` arithmetic and value-type constructors can never
  be references, so `ref_possible?/1` skips the wrapper for them. Readability
  of the generated source is a design goal, not a nicety.
- **A latent bug surfaced.** `reads?/2` had no clause for an index-target
  assignment, so `for x in xs: counts[x] = 1` reported `x` as unread, emitted
  `_x`, and then referenced it -- an undefined variable in generated code. The
  same analysis drives three other decisions, so the clause matters beyond this
  case.

**Sequencing:** the earlier recommendation to refuse `append` / `erase` is
superseded -- with the heap they are sound everywhere, and they shipped
alongside the rest of the methods.

### What the methods turned up

- **Not every method argument may be loaded.** `d.merge(other)` consumes the
  argument structurally and needs the contents, but `xs.append(inner)` must
  store the *reference* -- that is what makes a nested collection alias
  correctly. Loading uniformly silently broke `merge`; the two cases are now
  separated by name.
- **Method results are almost never references**, so wrapping them in `gd_load`
  produced `gd_truthy(gd_load(gd_has(...)))`. Only the five that build a fresh
  collection (`keys`, `values`, `split`, `duplicate`, `slice`) are reboxed, and
  `ref_possible?/1` knows the difference.
- **`gd_put` had to leave the always-on heap set.** A module that mutates only
  through methods never emits an element assignment, so `gd_put` came out
  unused and warned.

### What the last batch turned up

- **Helper dependencies had to become a closure.** They were resolved by an
  ordered chain of one-shot checks, which silently missed `gd_parsed` -- only
  `gd_to_int` needs it, and only `gd_format` needs *that*, and only `gd_mod`
  needs `gd_format`. `@helper_deps` plus a fixpoint replaced it. One dependency
  stays outside the map because it is mode-dependent: `+` reboxes only in
  reference mode.
- **The single-clause helper rule was broken when the methods landed**, and it
  bit here. Elixir's type checker narrows a multi-clause helper from the call
  sites in the generated module and then warns a clause is unreachable, so
  `floor(2.7)` was enough to produce a warning. All 27 method helpers were
  rewritten single-clause.
- **`/` and `%` were never load-wrapped.** Only `+`, `-`, `*` and `==` were,
  so in reference mode `"%s" % [a]` handed `gd_format` a reference and crashed
  on a tuple. `%` now *dereferences* its right-hand side, because a format
  argument list has to be plain all the way down, not just at the top.
- **Constant folding belongs in the AST, not at emission.** Resolving `const`
  and enum members inside `gen_expression` left the helper scan looking at the
  unfolded tree, so `Tier.SILVER` still pulled in `gd_get` and emitted it
  unused. A folding pass before codegen fixed it, and made the shadowing check
  (`var MAX` where `MAX` is a constant) a natural place rather than an
  afterthought.
- **`~s(...)` keeps biting.** Twice now a sigil containing balanced parens has
  swallowed its own delimiter. Plain strings with escaped quotes for anything
  containing `(`.

### Coverage

211 compiler tests in `sdk_tools/test/`, plus 11 for `Gamend.Signals` in the
core suite -- a new context with no tests was the largest gap when the batch
was called finished. The example plugin exercises constants, enums, `match`
destructuring, methods, reference semantics, `spawn`/`await` and a signal
crossing from `after_user_register` to a waiting process, and is checked
against a running server.

Three bugs surfaced while writing the tests rather than the features:

- **Enum members could not be used as `match` patterns** (`Tier.GOLD:`), which
  is ordinary GDScript. Patterns are parsed before constant folding, so the
  parser now keeps the reference and codegen refuses it if it did not fold.
- **A ternary inside a list or an argument list emitted invalid Elixir** --
  a bare `if ..., do: ..., else: ...` is ambiguous to the parser inside a
  container. Now parenthesised.
- **Generated code must not pattern-match narrowly on an SDK stub's result.**
  `case Signals.await(...) do {:ok, p} -> p; {:error, :timeout} -> nil end`
  drew "this clause will never match" in a plugin build, because a stub's
  inferred return type is narrower than its `@spec`. A catch-all fixes it, and
  the rule applies to any generated call into the SDK.

### What classes and `callv` turned up

- **`.call` was already taken.** `Gamend.Hooks.call/1,2,3` is a real function,
  so dynamic dispatch could not use that name. `callv` is the genuine GDScript
  spelling for "call by name with an array of arguments" and collides with
  nothing.
- **`Foo.new(...)` reads as a context call to anything that only looks at the
  name.** The helper scan boxed its result because `Foo` is PascalCase, which
  emitted an unused `gd_box`. No context exposes a `new`, so that is the
  discriminator.
- **Helper requirements had three separate coupling bugs**, all the same shape:
  a helper emitted by something the AST scan cannot see. The class constructor
  and dispatcher emit `gd_index` and `gd_put` with no node saying so; a
  mutating method emits `gd_store` while collecting only its own helper; and a
  class that never assigns a field must not pull the store pair in at all.
  Each is now tied to a precise question -- does any method read a field, does
  any method write one, is any method actually called -- rather than to the
  mere presence of a class.
- **`gd_self` has to be underscored when a method never touches a field**, or
  the generated code warns on an unused parameter. That is the fifth distinct
  place this session where emitting *source* let the Elixir compiler find a
  codegen slip for free.

### Would writing an existing plugin in GDScript pay? Measured against gamend_polyglot

The question was asked of a real 43k-line Elixir hook plugin. The answer was
no, and the perf question turned out to be moot -- it could not have been
written at all.

**Four structural blockers, three of which are now gone.** No cross-script
calls (66 files, 311 cross-module calls) -- **fixed**. No higher-order `Enum`
(1,358 `Enum.` calls, 681 anonymous functions) -- **fixed**, since Godot has
`map`/`filter`/`reduce` and we simply had not implemented them. No compile-time
data loading (6 files decode JSON at build time; `const` must be a scalar) --
still true. No processes (3 GenServers, 5 Supervisor references, 7 ETS uses;
`BoatGameServer` supervises its own tree) -- still true, and permanent.

**Performance, measured** (`sdk_tools/bench/`, M1) -- and the first two
measurements of this were both wrong, in the same way.

The first said "+16-46 ns per access, 2.6% on loops". True, but it measured
access *inside* a script and ignored the boundary.

The second said the boundary cost ~14x, scaling with payload size. That was an
artifact of the benchmark itself: it boxed in one long-lived process across
50,000 iterations, so the process dictionary grew to a million entries and
never shrank. A hook runs in its own Task and starts with an empty heap. Boxing
20 maps costs **9.5 us in a fresh process against 25.9 us in a polluted one** --
the harness was measuring the one caveat the design already documents
("temporaries live until the hook returns") and charging it to every call.

Measured properly, one fresh process per call, on a hook that reads 20 event
dictionaries:

| | before per-function boxing | after |
|---|---|---|
| value mode | 1.8x | 1.5-1.8x |
| reference mode | **8.2x** | **1.1-2.1x** |

**What closed the gap: boxing is decided per function, not per module.**
Reference mode is plugin-wide, but that never meant every function touches the
heap. A function boxes its arguments only if it can *reach* a reference --
an in-place mutation, a collection literal, a context call, an `await`, a
collection-returning method, or a call to another function that can. Everything
else skips the boundary entirely. In the benchmark, `score` was paying 8.2x
only because a neighbouring `touch` mutated; now it pays nothing.

The analysis is a fixpoint over the local call graph, and treats a cross-script
call as reaching a reference -- the callee may mutate, and handing it a plain
collection would silently transform a copy instead of writing through.

One follow-up remains: **scalars are still deref-wrapped.**
`min(gd_deref(max(gd_deref(count), 0)), 3)` -- `ref_possible?/1` cannot tell an
integer-holding variable from a collection-holding one. A dataflow pass would
narrow it. It matters much less now that most functions skip the boundary.

**The third measurement: whole hooks** (`sdk_tools/bench/hook_bench.exs`).
Everything above measures the *boundary*. It never measured a hook that
**creates** collections, which turns out to be where reference mode's cost
actually is. Median of 5, each candidate interleaved with its rival inside
every round, heap erased between calls, M1:

| hook | by hand | GDScript | |
|---|---|---|---|
| arithmetic and branching | 10 ns | 102 ns | value mode |
| read two fields, concatenate | 350 ns | 703 ns | 2.0x |
| build a string | 205 ns | 633 ns | 3.1x |
| read a payload, build 3 dicts, return | 134 ns | 4755 ns | 35x, reference mode |
| the same read-only hook, value -> reference | 570 ns | 604 ns | **1.1x** |
| ... with a 50-key payload | 510 ns | 530 ns | **1.0x** |

So the boundary really is close to free, as the table above it says. What is
not free is **creating** a collection: one `Process.put` with a brand-new key,
measured at 259 ns for one and 1305 ns for eight. The 35x row creates eight --
three boxing the payload, one for the Array, three for the Dictionaries in it,
one for the result -- and that is nearly all of its 4.8 us.

Two things put that in proportion. The server spawns a Task per hook, and that
Task costs ~3.1 us on this machine: a hand-written `register` hook measures
3131 ns end to end against an empty Task's 3149 ns, which is to say the body is
invisible. The GDScript one measures 8416 ns. And a hook that reads a payload
and calls gamend -- which is what hooks do -- never leaves value mode at all.

**The one number worth warning authors about is `xs.append(v)` in a loop.**

| | by hand, `Enum.map` | GDScript | by hand, same algorithm |
|---|---|---|---|
| 10 elements | 126 ns | 1848 ns | 580 ns |
| 100 elements | 1824 ns | 40 us | 21 us |
| 1000 elements | 15 us | 2.8 ms | 3.0 ms |

Against idiomatic Elixir that is 15x, 22x, 186x. Against the *same algorithm*
written by hand it is 4.4x, 1.7x, **1.2x** -- so at any size that matters this
is not the transpiler, it is the idiom: `append` copies the Array, which is
amortised O(1) on Godot's contiguous Array and O(n) on a BEAM list. A GDScript loop that
appends 1000 times does a million cons cells whoever wrote it. Compiling
append-only loops to a prepend and a reverse would fix it and is not yet done.

**Readability** is genuinely mixed. A real function translated to 23 GDScript
lines against ~20 Elixir, and the `with` chain became explicit early returns --
clearer to someone who does not read Elixir. But 2,211 pipes become temporary
variables, 860 multi-clause function names become `if`/`match` chains, and 922
guards vanish. Line-by-line more approachable; structurally flatter and
perhaps 1.5-2x longer.

The useful conclusion is about positioning, not perf: GDScript hooks are for a
Godot developer writing a *new* plugin without learning Elixir. A mature Elixir
codebase written by someone fluent in Elixir has nothing to gain.

### What Tier 1 turned up

Adding ~80 builtins at once made a latent gap load-bearing, and two of the
three findings were found by a probe rather than by a test.

- **Builtin calls were never arity-checked.** With ten builtins that was
  survivable; with eighty it is not. `clamp(a, b)` compiled happily and then
  failed as `undefined function gd_clamp/2` inside generated Elixir, which is
  the one thing this compiler promises never to do. Every builtin now carries
  its arity, and a mismatch names the `.gd` line. A test compares each
  declared arity against the helper it points at, so an edit to a helper
  cannot drift the table.
- **`range()` returned a `Range`, and only `for` ever noticed.** Godot returns
  an Array. `range(3).size()` answered **4** (it was counting the struct's
  fields), `range(3)[1]` answered `nil`, `.map()` answered `[]`, and
  `str(range(3))` printed `"0..2"` -- five silent divergences behind one
  correct-looking loop. It returns a list now, and takes the step argument it
  was always missing. Everything that only ever appears inside a `for` deserves
  a test that uses it as a value.
- **`print` and `str` were fixed-arity.** `print("score: ", score)` is what a
  Godot developer types on day one. They share the variadic path `min`/`max`
  already used.

And two codegen bugs that had been emitting warnings into generated modules
without failing anything:

- The reference helpers were selected by **re-deriving** where the generator
  would emit them -- "does any function take a parameter" standing in for "does
  any wrapper actually box". A function with no parameters, or one whose
  wrapper turned out not to need refs, got a `gd_box` it never called. This was
  the fourth instance of that drift in this file, so the rule changed rather
  than the condition: the ref helpers are now chosen by asking the **emitted
  code** what it calls, which cannot disagree with itself.
- The heap was **one helper source holding four functions**, so needing
  `gd_load` dragged in `gd_new` and `gd_deref` too. Split into four, with each
  stating only what it calls -- which also removed three dependencies
  `gd_mutate`, `gd_take` and `gd_spawn` never had.

The reason none of this failed a test: nothing asserted that generated code
compiles *silently*. `Code.put_compiler_option(:warnings_as_errors, true)` does
not reach `Code.compile_string/2`, so the warnings scrolled past. Every test
that loads a script now captures stderr and flunks on any output, which is how
the last two were found at all.

### The class surface: Tier 1 shipped, Tier 2 and 3 declined

"Which Godot classes are missing" sorts cleanly by whether the thing means
anything without an engine, and then by how often a server-side script reaches
for it.

**Tier 1 -- shipped.** `@GlobalScope`, `JSON`, `Time`, and the `Vector2` /
`Vector3` method sets. These are what a hook actually types: `clamp` a reward,
`lerp` a difficulty, `randi_range` a drop, stringify a payload, stamp a time,
measure a distance. `JSON` rides OTP's built-in `:json`, so it costs no
dependency. `min` / `max` are variadic and share helpers with `Array.min()` /
`Array.max()`, and `length()` dispatches at run time -- magnitude on a vector,
character count on a String.

**Tier 2 -- declined, and scripts get a compile error naming the line.**
`Vector2i` / `Vector3i` / `Vector4` / `Vector4i`, `Rect2` / `Rect2i`,
`RegEx`, `var_to_str` / `str_to_var`, `RandomNumberGenerator`. Each is real
work for a narrow payoff: the integer vectors are a separate value type and a
parallel method table for what `Vector2` already expresses; `RegEx` is a
Godot-flavoured wrapper over `:re` with different syntax; `var_to_str` is a
serialiser nobody needs when `JSON` is present; `RandomNumberGenerator` is a
seedable object when the global `randi` / `randf` already cover the use.

**Tier 3 -- declined on principle.** `StringName` and the `Packed*Array`
family are performance aliases for representations the BEAM does not have --
`split()` returns a plain Array and type hints are discarded, so an alias would
be a name with no behaviour behind it. Everything engine-side falls under the
one root cause below.

The cost of declining is bounded because the compiler refuses rather than
approximates: a script reaching for `Rect2` fails the build with a file and a
line, never at 3am in production.

### Cannot be built

After several rounds of narrowing, the list reduces to **one root cause**. Every
item below is a consequence of it, not a separate limit.

**There is no engine in the process.** Nothing here is a compiler limitation;
there is simply nothing to call. Reference semantics used to be a second root
cause; it shipped, and the list is down to this one.

| Ruled out by it | Nearest thing that works |
|---|---|
| `Node`, `Scene`, `Resource`, `Object` | plain Dictionaries and the gamend contexts |
| `preload` / `load`, the resource system | `Gamend.Storage`, `Gamend.KV` |
| physics, rendering, input | — (client-side concerns) |
| `Engine`, `OS`, `ProjectSettings` | plugin settings and env vars |
| `_ready`, `_process`, `_physics_process` — there are no frames | `Gamend.Schedule` (cron), `Gamend.Jobs` |
| `Thread`, `WorkerThreadPool` | `spawn()` / `await` — same capability on BEAM processes |
| per-object signals (`node.tree_exited`) | plugin-scoped signals (buildable, above) |
| `@export` as an inspector field | the admin-settings idea in Deferred |
| Godot's static typing, which is engine-aware | type hints over the subset's own types |

Only libgodot changes any of this, and that is a different product.

That is the whole list. An earlier revision had a second root cause, "no
shared mutable heap"; measuring it showed the heap is already there (see the
reference-semantics section above). The one residual it leaves -- a `spawn()`ed
lambda sees a snapshot rather than sharing -- is a cost tier, not a wall.

### Not impossible -- declined

One thing sits outside both root causes and is a **choice**, so it is recorded
here rather than above:

- **Unbounded `apply/3`** -- calling any Elixir module and function from a
  computed string. Perfectly emittable. It removes the compile-time whitelist,
  and with it both the build-time error on a typo and the "a script cannot
  express `File.rm/1`" property that any future hosting story would rest on.
  Dynamic dispatch *within* the API table gives the useful part without the
  cost, and is listed as buildable above.

## Deferred / rejected

- **Tree-walking interpreter: rejected.** Same front end, 10–100× slower, and
  it needs a runtime that the compiled path does not. The only thing it buys is
  easier error messages, and the generated-source approach already gives those.
- **Sandboxing: rejected for v1**, per the "not a sandbox" scope above. If
  gamend ever hosts other people's scripts this returns as a *codegen*
  whitelist (only ever emit calls in the API table) plus `max_heap_size` and a
  watchdog process — cheap to add later precisely because name resolution
  already goes through one table. Nothing in v1 forecloses it.
- **`@export` → admin-editable settings: defer, but this is the highest-value
  follow-up.** `@export var daily_reward := 100` surfacing as a hot-editable
  field in the admin portal is a LiveOps feature (it is roughly what Heroic
  Labs sells as Satori). It is deferred because it does not fit
  `Gamend.Settings.Provider` — that is env-var-derived and read-only at
  runtime, and `@export` needs a runtime-writable store. That is a KV-backed
  settings surface, which is its own spec.
- **Classes and inheritance: defer.** Hooks are a flat set of functions. Revisit
  when a real plugin has duplicated logic that only inheritance would remove.
- **Array index performance: accept for v1.** `arr[i]` emits `gd_index/2`,
  which is `Enum.at/2` on a list (O(n)). Document "use a Dictionary for hot
  lookups" and revisit with a per-variable representation pass only if a
  profile demands it.
- **Operator helpers: accept for v1.** `+`, `/`, `%` and every truthiness test
  go through a one-clause helper, because GDScript disagrees with Elixir on all
  four (string concat, integer division, `rem`, and `0`/`""`/`[]` being falsy).
  A later type-inference pass can specialise the cases it can prove numeric;
  until then correctness beats one function call on a path dominated by
  database writes.
- **libgodot / real Godot types: explicitly not this spec.** Running actual
  scenes and physics server-side is a separate, much larger product. Coupling
  it here would sink both.

## Appendix — why GDScript first, and what a second language would cost

GDScript is unusually cheap to transpile, and the reasons are specific:
Python-like surface syntax, no `this`, no prototypes, no metaclasses,
decorators or generators, a small stdlib, and — the decisive one —
`ClassName.method()` maps 1:1 onto `Module.function()`. Almost nothing else on
the shortlist has that property.

| Language | Route | Cost | Verdict |
|---|---|---|---|
| **GDScript** | transpile → Elixir source | low | **this spec** |
| **Lua** | embed [Luerl](https://github.com/rvirding/luerl) — Lua 5.x written *in Erlang* | very low (no compiler at all) | best second language. Each state is an Erlang term in a normal process; no NIF, no port. Nakama's scripting language, so it doubles as a migration story. Cost: interpreted, and Godot devs don't write Lua |
| **Wasm** | `wasmex` (Wasmtime NIF) | medium | the generic answer — unlocks Rust/Go/AssemblyScript at once. But every API call marshals across the boundary, which is the wrong shape for I/O-bound hooks that mostly call back into gamend |
| **JavaScript** | embed QuickJS via NIF, or a Deno port process | high | biggest audience, worst fit. Transpiling is hard (`this`, prototypes, async, closures over mutable locals); embedding means either an immature NIF or Supabase's edge-runtime shape — a separate process and IPC per call |
| **Python** | Pythonx / erlport (separate OS process) | high | transpiling is hardest of the set (dynamic everything); embedding CPython in BEAM is a non-starter (GIL, blocking). Worst ROI |
| **Gleam / LFE** | already compile to BEAM | **zero — verified** | shipped as `modules/plugins_examples/example_gleam`. Loads through the unmodified plugin path; the only change core needed was one RPC name lookup that used Elixir's `__info__/1`. Free, but nobody in this audience writes them |

Effort ranking: **GDScript ≪ Lua < Wasm < JavaScript ≪ Python.**

Gleam is already done — see the row above. It cost one line of core and a
bundling script, because hook dispatch was never Elixir-specific. That is worth
noting here because it sets the bar: any route that needs *more* than a
front-end and a bundler is buying something, and the appendix is how you check
what.

The strategic read: you do not need many. GDScript is both the easiest to build
and the one your audience already writes — do it first and alone. Lua via
Luerl is the natural second *if* Nakama refugees show up asking, because it
needs zero compiler work. Everything else should wait for someone to actually
ask twice.
