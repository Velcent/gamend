    • [fixed] Leaving a Stripe checkout no longer blocks the next one for a day. An entitlement or subscription has one open checkout at a time, and a Checkout Session the buyer walked away from (Back from the payment page, a closed tab) stayed requires_action until Stripe expired it, 24 hours later: picking yearly, going back and picking lifetime answered purchase_already_in_progress. A new Stripe checkout now expires every open Stripe session for the same entitlement (Stripe.expire_checkout_session/1, POST /v1/checkout/sessions/:id/expire, at the checkout API version), cancels its purchase as the checkout.session.expired webhook does, and goes ahead. Stripe expires only an open session, so one paid meanwhile is never cancelled: it is reconciled and fulfilled, and the new checkout answers already_owned; one whose payment is still clearing keeps refusing. Another provider's open purchase (Steam) is left alone and refuses as before, and a Steam checkout closes no Stripe one. New sessions also carry expires_at, 31 minutes out (Stripe's 30-minute floor plus a minute for clock skew), so an abandoned one lapses on its own; Managed Payments accepts it. A custom :stripe_adapter needs expire_checkout_session/1. Gamend.Payments.StripeCheckoutTest.

    • [fixed] A read in flight no longer caches a row from before a write. A read that missed the cache queried the row, then cached it; a write that committed and evicted the key in between evicted nothing, and the read then cached the old row until the TTL (60 s by default). The worst case: a request that loaded the user during a logout, password change or "log out everywhere" cached the old token_version, and GamendWeb.Auth.Guardian, which checks it through Accounts.get_user/1, kept accepting the revoked JWT (the re-cache in revoke_all_tokens/1 did not close it, the reader's put could land after it). The same race served old wallet balances, entitlements and KV values, and a read-modify-write under a lock could start from an old KV row and write it back. Gamend.Cache.invalidate/1 now moves a per-key generation before it deletes (also on other nodes, through Gamend.Cache.Sync), and Gamend.Cache.cached/3 caches what it read only if the generation did not move meanwhile; it also caches nothing inside a transaction and takes match:. generation/1 and fill/4 are the same check for a read-through of its own. Accounts.get_user/1 and get_user_by_field/2 use it instead of Nebulex's cacheable (the field index now caches the id, and an index left behind by a changed email or username falls back to the database), as does KV.get/2, so the economy and payments caches, which already went through cached/3, are covered too. KV writes only evict now: a writer that re-cached what it wrote could reach the cache after a later write. Gamend.CacheFillRaceTest stops a reader between its query and its put on a real cache; against the old code four of its five tests failed.

    • [changed] Callers waiting on a lock are served in order. Gamend.Lock.Local, the mutex behind Lock.serialize/3 on SQLite and in front of the Postgres advisory lock, was a :global.trans, whose waiters retry after a random sleep that doubles up to 8 s: the lock sat free while they slept. Forty callers taking one key ten times each, a millisecond inside, waited up to seconds; a host measured 50 players answering one shared row at once at 13 s for work that takes 2.4 s, with p99 at 7 s. Waiters now queue per key in Gamend.Lock.Queue (one partition per scheduler, started by HostSupervision.children/1 after Gamend.Repo), and the key passes to the next one when the holder finishes or dies; same reentrancy, same API. trans/2 still takes :global for the cluster, asked only by the head of each node's line. Hosts that start their own tree add Gamend.Lock.Queue; without it the old :global path is used. Gamend.LockLocalTest.
